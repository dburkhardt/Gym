# Creator bridge status and execution boundary

`creator_bridge.py` is a source-bound component, not a discoverable benchmark. It executes the pinned creator class and request/parser ASTs rather than copying an agent loop. Its one-pass local control preserves the actual creator prompt, extraction, history and program writing, uses Gym's existing durable guarded transport, and proves one429 cannot produce another physical request. The explicit fixture tokenizer is **not** evidence for a Nemotron tokenizer. No native runtime config or full integration claim is made.

## Sampling choice that must be explicit

The creator README94–98 documents GPT-4o and o1-preview through OpenAI, and other LLMs through Bedrock. `engine/base_engine.py` selects OpenAI for `gpt`/`o1`; `engine/openai_engine.py` sends temperature/top_p/max_tokens2000 only for `gpt`, omitting them in the other branch. `engine/bedrock_engine.py:7` passes maxTokens2000 plus the caller's temperature/topP for other models. `ScienceAgent.solve_task` and `step` supply0.2/0.95. Therefore routing the exact Nemotron name through the unmodified OpenAI function inherits the o1-style omission; that is not proof of the intended normal-model protocol.

The main component path is now the explicit `nemotron-normal-model-openai-v1` adaptation. It executes the separately checksummed Bedrock request function and maps its inferenceConfig to OpenAI max_tokens2000/temperature0.2/top_p0.95; the local creator-loop control checks those exact fields. It requires the declared exact Nemotron model. The original OpenAI branch is available only through explicit `diagnostic-creator-openai-branch`, not the default. This is a named model/transport adaptation, not published equivalence. The creator default direct prompting and optional self-debug remain distinct; the component supports only the former and refuses self-debug. Published aggregate best-of-three runs and the verifier's three visual samples are also distinct counts.

## Full bridge using existing Gym interfaces

The native agent should use existing guarded model references/capture lineage and an owned Sandbox, never the creator SDK's10 retries or unbounded backoff. A private solver workspace receives only the selected dataset subtree and submitted program. A qualified, immutable scientific image must provide the creator execution environment; no reference archive, metadata receipt, gold code, evaluation modules or credential files are mounted. Source/hash/runtime admission must occur before the first model request. The current preparation receipt deliberately cannot authorize execution.

For self-debug, preserve the creator loop unchanged and replace only its installation/execution boundary with sandbox calls. The creator performs dynamic `pipreqs`, dependency resolution and `pip-sync` before execution; that behavior is not reproduced by a generic Python image. An approved pinned resolver/cache/network policy and the actual verified archive are needed to qualify this boundary. Execution retains its900s timeout, error text,2000-token error trimming, unchanged-program stop and ten-step maximum. Do not execute generated Python on the controller while these assets are unavailable.

After prediction execution, stop and reconcile the solver sandbox before starting a separate trusted verifier sandbox. Transfer only confined output artifacts to a fresh verifier-owned directory, rejecting symlinks, devices, traversal and oversized/unexpected files; never reopen a solver mount after references are installed. The verifier alone receives gold/evaluation assets. CodeBERT may read prediction source as inert text, but trusted scoring must not re-execute that source in the reference-bearing sandbox. The pinned `compute_scores` currently executes it after CodeBERT and alongside reference paths, so direct invocation is unsafe. A source-guarded small phase split must preserve execution-status/output-existence handling and eval return tuples while documenting the changed order; it cannot be qualified until private eval scripts and their auxiliary imports are available for review. Do not pretend a substring check on filenames proves isolation.

`visual_judge` already executes the pinned visual prompt/parser with an explicit model-name substitution through the same durable transport. It retains n=3,0.2/0.95/max_tokens1000, predicted-image-first ordering and averaging (including zero for an unparsable textual sample); the local control proves those settings. It refuses missing/nontext choices instead of silently reducing the denominator. Only the trusted verifier phase may call it with gold images. Real endpoint support for n=3 and visual content remains unqualified; splitting one request into three calls would require an explicit adaptation, not a hidden fallback.

## Concrete remaining blockers

The exact verified archive remains inaccessible in retained evidence; no authenticated publisher archive checksum or auxiliary-evaluator closure is available. No qualified scientific image matching these tasks has been established. No verified exact Nemotron tokenizer/trim implementation has been supplied; a caller string alone is not attestation. These prevent safely wiring a runnable agent/resource now. They do not prevent the frozen preparation, source-bound one-pass transport and visual parser controls already implemented. Next implementation after assets are supplied is the prediction/verifier phase split and sandbox failure/cleanup controls, followed by actual native local-provider qualification. No new scheduler or replacement dataset is needed.
