## Separately named creator parser and merge contract

`creator_protocol.py` implements `csmed-ft-creator-chunk-labels-81cd354`, independently of the existing whole-paper strict-label grader. Source parity controls extract only the two pure functions from pinned creator commit `81cd35498bdea8981e5310842c32398625a10e95` and verify both file SHA256 hashes; they never import its API-key-reading module. The parser lowercases without stripping whitespace, accepts included/include/yes and excluded/exclude/no, and marks everything else -1. The paper merge returns excluded if any chunk is excluded, otherwise included—even when every chunk is invalid. It retains the first reference label and exposes conflicting references and invalid chunk counts. Those creator quirks are preserved, not endorsed as measurement quality. This module does not change existing scores or enable a canonical generation run.

Canonical generation still needs the original review title, review criteria, paper title, abstract, main text, review/paper IDs and integer dataset row identity. The creator constructs `Systematic review:` and `Candidate paper:` text, uses `tiktoken.encoding_for_model(model_name)` and LangChain `TokenTextSplitter` with zero overlap, truncates the review to its first half-context chunk, and splits the paper at `max(context_size // 2, context_size - original_review_token_count)`. Crucially, that token count precedes review truncation. Each paper chunk receives the original eligibility question and `Answer: ` suffix; predictions must retain paper and chunk identities before merging. A whole-paper response cannot reconstruct these unobserved chunk responses.

The selected upstream example is GPT-3.5-Turbo-16k with a 16,000-token window; the script also defines 4,000/8,000-token alternatives. A Nemotron run needs an explicitly declared tokenizer/context-window adaptation, pinned splitter/tokenizer versions, and frozen chunk/prompt hashes. It cannot inherit a GPT tokenizer by accident or claim creator-model reproduction. Upstream leaves temperature/output cap at API defaults; the campaign's 0.3/16,384 settings are a separate variant. Upstream unbounded exception retry must not replace Gym's uncertainty guard. Canonical reporting additionally requires the creator's accuracy, macro precision/recall, binary/macro/micro F1 and macro F3 over merged papers, with explicit invalid-chunk and conflicting-reference dispositions. None of these generation or reporting gates is closed by parser parity alone.

The separate `creator_chunks.yaml` uses native preparation and a specifically selected chunk parser; scalar aggregation is disabled because chunk correctness is not paper accuracy. Set `CSMED_CREATOR_RECIPE` to JSON containing `recipe_model`, `application: creator-tokenizer-adaptation`, `dataset_zip`, `dataset_sha256`, `frozen_selection`, `selection_sha256`, `tokenizer_cache_dir`, and `tokenizer_asset_sha256`. Preparation requires exact `tiktoken==0.4.0` and `langchain==0.0.191`, and `TIKTOKEN_CACHE_DIR` must equal the declared absolute cache directory containing the preexisting cl100k asset. Missing assets/dependencies refuse preparation; this path never fetches tokenizer data. It preserves original paper/review IDs, introduces explicit per-paper chunk ordinals, and publishes a hash-bound provenance receipt using shared staging. No live run of this adaptation is authorized or qualified by these controls.

`grouped_report.report(materialized_inputs, native_outputs)` computes the seven creator metrics only over complete paper groups, with separate expected/received chunk and scored/unresolved paper counts. Missing response groups are unscored, never converted to model-error zeros. Duplicate or mixed-recipe/reference outputs refuse reporting. Invalid textual answers remain -1 before the original merge; all-invalid papers can therefore receive an included prediction under the creator protocol. This is explicitly retained as a protocol limitation. Local controls verify parser/merge and metric parity. Actual tokenizer-dependent materialization was subsequently qualified in an isolated Python 3.11 environment for the first frozen 20 papers (21 chunks), with network access disabled and byte-exact comparison against the creator source. This does not qualify model execution.

The recipe must also declare `generation_protocol` containing the exact returned `model` identity, `temperature`, and `max_output_tokens`. Group reporting compares typed actual input messages against materialized messages (allowing only schema defaults), and checks these actual model/settings; copied metadata cannot legitimize a changed prompt. Reporting needs `requirements-report.txt` (validated local scikit-learn 1.9.1); the creator specified ~=1.2.2, so reports record the actual metric-library version. Source-formula parity is not a claim of a byte-identical creator environment. `requirements-tokenizer.txt` identifies the separate creator-era dependency requirements; do not install these over active Gym components. The isolated qualification uses the pinned creator-era environment and asset described below; other environments must pass the same checks.


### Qualified preparation environment

The isolated acceptance used Python 3.11.16, tiktoken 0.4.0, LangChain 0.0.191, pandas 1.5.3 and datasets 2.8.0. The cl100k asset is 1,681,126 bytes, SHA256 `223921b76ee99bde995b7ff738513eef100fb51d18c93597a113bcffe865b2a7`. These exact versions are declared in `requirements-tokenizer.txt`; the resolved environment is recorded with the acceptance artifacts. Set `CSMED_CREATOR_PYTHON` to that isolated interpreter when invoking native preparation. Explicit interpreters are always delegated to, even when two venv symlinks resolve to the same base Python.

Preparation now mirrors pandas followed by the creator's Hugging Face string-feature encoding. Missing title/abstract values become literal `nan`, not empty strings. The affected frozen20 paper IDs are `CD014821-bib-0007`, `CD013649-bib-0018`, and `CD010452-bib-0012`; their prompts passed actual creator-loader/tokenizer comparison. Missing main text remains an explicit invalid-input refusal even if metadata incorrectly claims validity. No papers are silently removed. Preparation receipts record source/output hashes, implementation hash and runtime versions. Full frozen50 invalid-input disposition and model generation remain separate gates; this qualification covers exactly the first20 papers,21chunks.

The subsequent full frozen50 offline check accounts for every paper: 47 valid papers produce 49 chunks with exact creator prompt parity. Three remain blocked: `CD015016-bib-0025` and `CD015016-bib-0002` lack eligibility criteria; `CD013778-bib-0186` lacks full text. Whole-selection preparation refuses and publishes no dataset. These cases were not dropped or scored zero, and no filtered collection was admitted. Both qualification runs disabled network connections during materialization and made zero model calls.
